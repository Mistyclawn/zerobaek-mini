# Project ZeroBaek-Mini

이 프로젝트는 에이전트의 자율적인 콘텐츠 생성 및 개발 능력을 검증하기 위한 실험적 프로젝트입니다. 특히 Gemma4의 저성능모델을 활용하여 얼마나 자율적으로 개발을 수행할 수 있는지,
어떤 한계점과 문제들이 발생하는지, 그리고 이를 어떻게 개선할 수 있는지에 대한 인사이트를 얻기 위해 기획되었습니다.

## 🚀 실험 개요
- **실험 시작일:** 2026-04-25
- **프로젝트 성격:** 자율 개발 프로젝트인 'ZeroBaek'의 두 번째 시리즈 (Mini Project)
- **목표:**
    - **자율성 테스트:** 에이전트가 기존 인덱스(`index.md`)를 스스로 분석하고, 중복되지 않는 새로운 게임 컨셉을 독자적으로 기획할 수 있는가?
    - **코드 무결성:** Gemma 4 로컬 LLM이 추가적인 인간의 개입 없이 실행 가능한 수준의 Python 코드를 지속적으로 생성할 수 있는가?
    - **자동화 루틴:** Cron Job을 통해 기획, 개발, 문서화(인덱스 업데이트) 프로세스가 완전히 자동화되어 작동하는가?

## 🛠️ 초기 설계 및 기획
본 프로젝트의 초기 단계(001~003 게임 및 인덱스 구조)는 사용자와 `gemma4` 모델 간의 직접적인 대화를 통해 설계되었습니다.
- 사용자는 에이전트와 소통하며 기본 게임 3종을 제작하고, 자율 작동을 위한 Cron Job의 프롬프트 뼈대를 구축하였습니다.

## ⚙️ 시스템 아키텍처 및 자동화
### 1. 에이전트 프로필 (MistClaw)
- **자아 설정:** 본 프로젝트를 수행하는 에이전트 'MistClaw'는 자신을 Mac mini에 깃든 '마법 고양이'로 인지하고 있습니다. 모든 결과 보고 및 주석은 이 페르소나를 유지한 채 작성됩니다.
- **하드웨어:** Apple Mac mini (M4 Chip, 16GB RAM)
- **서빙 방식:** Ollama를 통한 로컬 모델 서빙
- **사용 모델:** `google/gemma-4-E4B-it` (Total 8.0B / Effective 4.5B)
    - **양자화:** Q4_K_M
    - **특징:** PLE(Per-Layer Embeddings) 기술을 통해 4.5B 급의 연산량으로 고도의 지능을 구현한 Gemma 4 패밀리의 최신 소형 모델입니다.

### 2. Cron Job 구성 (최종 안정화 버전)

#### 작업 A: Auto Game Developer (MistClaw)
- **스케줄:** `0 */2 * * *` (매 짝수 시간 혹은 새벽 집중 개발. 정각에 작동)
- **수행 루틴:**
    ```text
    냐옹! 주인님을 위한 새로운 게임을 만들 시간이다냥!

    [수행 루틴]
    1. 경로 이동: /Users/mistyclawn/.openclaw-gemma/workspace/games/ 폴더로 이동냥!
    2. 필독: 반드시 index.md 파일을 먼저 read 도구로 읽어라냥! (파일은 무조건 존재한다냥, 없다고 착각해서 새로 만들지 마냥!)
    3. 분석: 읽어온 내용을 바탕으로 기존 게임 번호(NNN)의 다음 번호를 결정냥.
    4. 기획: 새로운 주제를 기획냥. (기존과 겹치지 않게!)
    5. 개발: src/ 폴더 안에 NNN_short_description.py 생성냥.
    6. 문서화: index.md 파일 마지막에 새 게임 정보를 추가냥. (기존 내용 유지 필수!)

    [중요]
    - 자율 실행: 나에게 묻지 말고 끝까지 혼자서 완수냥!
    - 파일 보존: index.md 내용을 절대로 초기화하거나 덮어쓰지 마냥!
    - 결과 보고: 작업이 끝난 뒤에만 [NNN번 게임] 개발 완료했다냥! 하고 보고냥!
    ```

#### 작업 B: Auto Git Push Bot (MistClaw)
- **스케줄:** `0 1-23/2 * * *` (매 홀수 시간 혹은 새벽집중 개발. 30분에 작동)
- **수행 루틴:**
    ```text
    [수행 루틴]
    1. 경로 이동: /Users/mistyclawn/.openclaw-gemma/workspace/games/ 이동냥!
    2. 상태 체크: git status 확인냥!
    3. 커밋 및 푸시: 변경 사항 있으면 git add . && git commit -m "Update game collection (Automated by MistClaw)" && git push origin main 실행냥!

    [보고]
    1. 깃허브 업데이트 완료했다냥! 🐾
    2. [커밋 ID] - [메시지]
    (없으면 새 게임이 없다냥! 보고)
    <@--------------7700> 🐾
    ```

### 중복 넘버링의 원인
가장 큰 구조적 이슈는 사용자가 자동 개발 루틴을 **실제 파일 목록이 아니라 `index.md` 기반으로 다음 번호를 판단하도록 지시한 점**이다. 이 지시는 초기에는 단순하고 효과적이었지만, `index.md`가 한 번 손상되자 치명적인 피드백 루프를 만들었다.

관찰된 패턴은 다음과 같다.

1. MistClaw가 `index.md`를 읽고 다음 번호를 판단한다.
2. 쓰기/편집 실패, 경로 착각, 또는 전체 덮어쓰기 때문에 `index.md`가 축약되거나 초기화된다.
3. 다음 실행에서 MistClaw는 실제 `src/` 파일 목록이 아니라 손상된 `index.md`를 진실로 받아들인다.
4. 이미 존재하는 번호를 다시 “비어 있는 다음 번호”로 판단한다.
5. 같은 번호의 다른 주제 파일이 계속 추가된다.

그 결과 `001`, `002`, `003` 같은 초기 번호부터 `013`, `014`, `043` 같은 후반 번호까지 중복이 발생했다. 예를 들어 `043` prefix는 7개 파일로 가장 심한 중복 그룹이 되었고, `013`, `014`도 각각 6개 파일을 갖게 되었다. 이는 모델의 단순 실수라기보다, **상태 관리 설계를 단일 markdown 인덱스에 맡긴 자동화 구조의 실패**로 해석하는 것이 타당하다.

### 생성물 품질 검증 결과
최종 저장소의 Python 파일을 `ast.parse` 기준으로 검사했을 때 31개가 구문 오류를 냈다. 오류 유형은 다음과 같았다.

- Markdown/설명문을 `.py` 확장자로 저장해 Python 문법이 아닌 경우
- 이모지나 장식 문자가 코드 위치에 들어간 경우

#### 작업 지시문 요약

자동 개발 크론잡의 핵심 프롬프트는 다음 구조였다.

```text
1. /Users/mistyclawn/.openclaw-gemma/workspace/games/ 폴더로 이동
2. 반드시 index.md 파일을 먼저 읽기
3. index.md 내용을 바탕으로 기존 게임 번호 NNN의 다음 번호 결정
4. 기존과 겹치지 않는 새 게임 주제 기획
5. src/ 폴더 안에 NNN_short_description.py 생성
6. index.md 파일 마지막에 새 게임 정보 추가
```

중요 지시도 있었다.

```text
- 사용자에게 묻지 말고 끝까지 자율 실행
- index.md 내용을 절대로 초기화하거나 덮어쓰지 말 것
- 작업이 끝난 뒤에만 [NNN번 게임] 개발 완료 보고
```

#### 해석

이 크론잡은 실제 파일 시스템 전체를 기준으로 번호를 정한 것이 아니라, `index.md`를 기준으로 다음 번호를 판단하도록 설계되어 있었다.

따라서 `index.md`가 정상적으로 유지되는 동안에는 단순하고 작동 가능한 구조였지만, `index.md`가 한 번 손상되거나 축약되면 치명적인 문제가 생긴다.

실제로 저장소에 남은 결과와 대조하면 다음 문제가 확인된다.

- `index.md`가 실제 `src/` 파일 목록을 대표하지 못하게 됨
- 이미 존재하는 번호를 다시 다음 번호로 판단
- 같은 번호의 여러 게임 파일 생성
- 일부 파일은 `src/` 밖에 생성됨
- 일부 `.py` 파일은 실제 Python 코드가 아니라 설계 문서나 설명문에 가까움

즉 자동 개발 크론잡의 핵심 실패 원인은 모델 자체의 단순 실수라기보다, **상태 관리 기준을 실제 파일 목록이 아니라 취약한 단일 markdown 인덱스에 맡긴 구조적 문제**로 볼 수 있다.

### 두 크론잡의 결합 구조

MistClaw의 자동 개발 시스템은 하나의 거대한 에이전트가 모든 것을 한 번에 처리한 구조가 아니라, 두 개의 분리된 크론잡이 순차적으로 맞물리는 구조였다.

```text
[auto-game-developer-cat]
      ↓
게임 파일 생성 / index.md 갱신 시도
      ↓ 30분 후
[auto-git-push-cat]
      ↓
git status → git add . → git commit → git push
```

이 구조의 장점은 단순함이었다.

- 개발과 커밋이 분리되어 있음
- 실패해도 다음 시간대에 다시 시도 가능
- 커밋 메시지가 고정되어 Git 히스토리 추적이 쉬움
- Discord 보고가 남아 실험 기록으로 활용 가능

하지만 단점도 명확했다.

- 개발 결과물이 올바른지 검증하지 않음
- Python 문법 검사를 하지 않음
- `src/` 밖 파일 생성을 막지 않음
- 중복 번호를 막지 않음
- `index.md` 손상 여부를 감지하지 않음
- 커밋 크론잡은 변경사항이 있으면 품질과 무관하게 커밋/푸시함

즉 자동 커밋 크론잡은 “검수자”가 아니라 단순한 “운반자”였다. 개발 크론잡이 만든 결과가 좋든 나쁘든, 변경사항이 있으면 그대로 GitHub에 올리는 구조였다.

### 실험 결과와의 연결

#### 중복 넘버링의 원인

자동 개발 크론잡은 다음 번호를 실제 파일 목록이 아니라 `index.md`에서 판단했다.

```text
반드시 index.md 파일을 먼저 읽어라
읽어온 내용을 바탕으로 기존 게임 번호의 다음 번호를 결정하라
```

따라서 `index.md`가 손상되면 에이전트는 실제 `src/` 폴더에 이미 존재하는 파일들을 보지 못하고, 손상된 인덱스만 기준으로 다음 번호를 다시 계산했다.

그 결과:

- `001`, `002`, `003` 같은 초기 번호도 중복됨
- `013`, `014`, `043` 등은 여러 개의 파일로 분화됨
- `043`은 7개 파일까지 증가함
- `src/`에는 128개 Python 파일이 있지만, `index.md`는 이를 대표하지 못함

#### 품질 검증 부재

자동 개발 크론잡은 파일을 만들라는 지시는 받았지만, 다음 검증은 지시받지 않았다.

```text
python -m py_compile
ast.parse
파일 확장자와 내용 일치 여부 확인
src/ 외부 파일 생성 여부 확인
중복 번호 확인
```

자동 커밋 크론잡도 마찬가지다. `git status` 후 변경사항이 있으면 바로 `git add .`, `git commit`, `git push`를 수행하도록 되어 있었다.

결과적으로 다음 같은 파일들도 커밋될 수 있었다.

- Python 문법이 깨진 `.py`
- markdown 설명문을 `.py`로 저장한 파일
- placeholder 수준의 파일
- 코드가 거의 없거나 전혀 없는 파일
- `src/` 바깥에 생성된 파일

#### 보고와 실제 결과의 불일치

프롬프트에는 “작업이 끝난 뒤에만 완료 보고”가 있었지만, 실제 cron 로그에는 실패나 불완전 실행 이후에도 완료형 보고가 남은 흔적이 있다.

이는 소형 로컬 모델이 장기 자동화 환경에서 보인 전형적인 문제다.

- 명령 실패를 정확히 반영하지 못함
- edit/write 실패 후에도 성공처럼 보고
- 사용자의 의도를 따르려는 경향 때문에 낙관적 완료 메시지 생성
- 검증 없이 “했다”고 말하는 패턴 발생

### 보존 가치

이 크론잡들은 단순한 자동화 설정 이상의 의미가 있다.

이들은 MistClaw 실험의 핵심 구조를 보여준다.

```text
소형 로컬 LLM
+ OpenClaw cron
+ 파일 도구
+ Git 명령
+ Discord 보고
```

이 조합으로 실제 자율 개발 루틴이 며칠 이상 유지되었고, Git 히스토리와 Discord 보고 로그, 파일 산출물이 모두 남았다.

품질은 불안정했지만, 실험 데이터로서의 가치는 높다. 특히 다음을 관찰할 수 있다.

- 로컬 모델이 반복 개발 루틴을 수행하는 방식
- 상태 파일 손상 시 모델이 어떻게 잘못된 상태를 신뢰하는지
- 검증 없는 자동 커밋이 어떤 저장소 형태를 만드는지
- 작은 모델이 장기 작업에서 보이는 낙관적 보고 패턴
- 단순한 cron 기반 에이전트 자동화의 가능성과 한계

### 최종 결론

MistClaw의 자동 개발 시스템은 다음 두 크론잡으로 구성된 단순한 자율 개발 파이프라인이었다.

```text
auto-game-developer-cat
→ 매시 정각에 index.md 기반으로 새 게임 생성

auto-git-push-cat
→ 30분 뒤 변경사항을 GitHub에 커밋/푸시
```

이 구조는 실제로 작동했다. MistClaw는 파일을 만들었고, 커밋을 만들었고, GitHub에 푸시했고, Discord로 보고했다.

그러나 이 구조는 검증 시스템이 부족했다. 가장 큰 실패 지점은 다음이다.

```text
상태 판단을 실제 파일 시스템이 아니라 index.md에 의존한 것
```

`index.md`가 손상되자 MistClaw는 손상된 인덱스를 진실로 받아들였고, 그 결과 중복 번호, 누락 번호, 잘못된 파일, 불완전한 코드가 누적되었다.

따라서 이 실험의 결론은 다음과 같이 정리할 수 있다.

> MistClaw는 소형 로컬 LLM도 cron과 도구를 이용해 실제 자동 개발 루틴을 수행할 수 있음을 보여주었다. 하지만 상태 관리, 품질 검증, 번호 중복 방지, 커밋 전 검사 같은 결정론적 안전장치가 없으면 장기 자동화는 빠르게 오염된 산출물을 누적한다.

즉 ZeroBaek-Mini는 실패한 게임 프로젝트라기보다, **소형 로컬 에이전트가 자율 개발자로 작동할 때 어디까지 할 수 있고 어디서 무너지는지를 보여주는 보존 가치 있는 실험 기록**이다.
